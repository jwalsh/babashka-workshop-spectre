* How these are worked here

This section, and the /Working it here/ under each exercise, are local to this checkout. The exercise text is the workshop's.

The order, for every exercise: map it, load it, read the docs for the calls it names, try them from the file's ~(comment ...)~ block, and only then fill the stub and run its tests.

| step                                | with                                                                                                 |
|-------------------------------------+------------------------------------------------------------------------------------------------------|
| what loading the namespace pulls in | ~gmake namespaces NS=spectre.db~                                                                     |
| the stubs, each with its form       | ~gmake todos E=e3~ (~SRC=1~ leaves the tests out)                                                    |
| who calls a stub                    | the map under each exercise; ~clojure-lsp references --from spectre.db/load-db~ redraws it           |
| load the file                       | ~C-c C-k~. A stub file loads: its functions exist and return ~nil~                                   |
| evaluate one form                   | ~C-x C-e~ after it, or ~C-c C-c~ inside it. In a ~comment~ block that is the one form, not the block |
| the exercise's tests                | ~gmake e3~, or ~M-x spectre-test-ns~ from the source buffer or its test                              |

** Documentation for a call

The TODOs name library calls: ~fs/which~, ~p/shell~, ~edn/read-string~. What follows was checked against babashka's own nREPL, the one ~gmake demo~, ~gmake session~ and ~M-x spectre-jack-in~ start.

Load the file first. ~fs/which~ is an alias, resolved through the namespace of the buffer you are in. Until ~C-c C-k~ has created that namespace in the REPL, ~C-c C-d d~ on it finds nothing. A full name, ~babashka.fs/which~, resolves at any time.

| want                                     | do                                                        |
|------------------------------------------+-----------------------------------------------------------|
| docstring and arguments                  | ~C-c C-d d~ with point on the symbol                      |
| arguments while typing                   | nothing: eldoc puts them in the echo area                 |
| the names in a library                   | complete after ~fs/~, or ~(clojure.repl/dir babashka.fs)~ |
| find a name                              | ~(clojure.repl/apropos "which")~                          |
| the source                               | ~(clojure.repl/source fs/which)~                          |
| the call in use                          | [[file:src/tour.clj][src/tour.clj]]: evaluate its examples in place              |
| a ~clojure.core~ function on ClojureDocs | ~C-c C-d w~, in the browser                               |

~doc~, ~dir~ and ~source~ print: the text lands in the REPL buffer and the value is ~nil~. The ~comment~ blocks of [[file:src/spectre/clipboard.clj][clipboard.clj]] and [[file:src/spectre/db.clj][db.clj]] open with these lookups for the calls their TODOs name.

A process started with ~p/shell~ inherits the REPL server's standard output, so what it prints shows up in the ~*nrepl-server ...*~ buffer and not at point. ~p/sh~, or ~{:out :string}~, hands it back as a value.

Babashka's nREPL has no cider-nrepl, so these do not work on it: ~C-c C-d a~ and ~C-c C-d s~ (apropos), ~C-c C-d c~ (ClojureDocs in a buffer), ~C-c RET~ (macroexpand). ~M-.~ cannot open a ~babashka.*~ function either: that REPL names a file which is not on disk, and gives no line number for anything.

The JVM REPL has all of it. ~M-x spectre-nrepl-jvm~, or ~gmake nrepl-jvm~ and then ~M-x spectre-connect~, serves the same code from JVM Clojure with cider-nrepl: there ~fs/which~ points at line 1706 of ~fs.cljc~ inside the library's jar. It needs the ~clojure~ CLI, takes the fixed port, and writes ~.nrepl-port~, so do not start it in a checkout whose jacked-in REPL you still want ~brepl~ to find.

** Working it here

- ~.envrc~ points bbin at this checkout: ~BABASHKA_BBIN_BIN_DIR~ is ~.bin~ here, ignored by git and first on ~PATH~ while you are inside the checkout. ~bbin install .~ puts the launcher there and leaves your own bin directory alone.
- So the bbin launcher is on ~PATH~ only inside the checkout: direnv takes ~.bin~ off again when you leave. "From another directory" then means the manual launcher, or ~.bin/pw~ by its full path. This follows from how direnv works; E6 has not been done here to confirm it.
- ~gmake e6~ checks that a ~pw~ is on ~PATH~ and runs ~pw --help~ from ~/~. It keeps the ~PATH~ it started with, so it passes where a shell that really left the checkout would not find the bbin launcher.
- This exercise edits ~bb.edn~ and adds ~deps.edn~. The rule in ~AGENTS.md~ about leaving ~bb.edn~ alone is about where dev tooling goes, not about this.
