#+TITLE: Babashka Workshop - Spectre

Build a password manager with Babashka:

- The stateless [[https://spectre.app/][Spectre password algorithm]]. See the [[https://spectre.app/spectre-algorithm.pdf][algorithm description]].
- Local storage for site settings, with a terminal UI for editing them.
- A command-line interface for generating passwords.
- Babashka extensions for native scrypt implementations.

* Prerequisites

Install the following:

- [[https://github.com/babashka/babashka#installation][Babashka]], with FFI support if you want to use the libsodium implementation (>= 1.13.220, latest recommended).
  - Set up zsh completions with:
    ~source <(bb org.babashka.cli/completions snippet --shell zsh --prog bb)~.
    See https://github.com/babashka/cli#completions for other shells.
- Java 17 or later. FFI requires Java 22 or later.
- [[https://clojure.org/guides/install_clojure][Clojure CLI]] (optional).
- [[https://github.com/babashka/bbin#installation][bbin]] for E6.
- OpenSSL 3 or later, unless you use the FFI implementation.
- [[https://libsodium.gitbook.io/doc/installation][libsodium]] for the FFI implementation

On macOS, install OpenSSL with ~brew install openssl~. The system OpenSSL version is not compatible.

On Windows 10 or later, install OpenSSL with ~winget install openssl~.

* Working in this checkout

Everything from here to the license is local to this fork: tooling for working through the workshop, not part of it. The workshop's code is ~src/~ and ~test/~, and ~bb.edn~ is untouched.

** The method

REPL first. Read a namespace, load it, read the docs for the calls it uses, and try them from the file's ~(comment ...)~ block. The test, or the stub, comes after that, and says what the exploration already showed.

So the tooling is about seeing: what a namespace loads, who calls a stub, what a library call returns, what the editor and the REPL are doing right now. [[file:exercises.org][exercises.org]] carries that for each exercise under /Working it here/, and how to look up documentation for the ~babashka.fs~ and ~babashka.process~ calls the stubs name.

** Start

#+begin_src sh :eval no
gmake deps          # what the workshop needs, and what is installed
gmake .env          # the throwaway identity the tests use; never overwrites
direnv allow        # this checkout's own db.edn, nREPL port and bbin directory
gmake demo          # Emacs in a frame, jacked in to babashka, core.clj loaded
gmake status        # is the REPL live, and is it this checkout's
#+end_src

~gmake session~ is ~gmake demo~ inside a detached tmux session, which an agent can read with ~gmake session-shot~. Either way ~brepl -e '(form)'~ evaluates in the same REPL from a shell.

** Parts built from the files

Two things a document here keeps saying are in the files already: which files there are, and which namespace loads which. ~gmake files~ and ~gmake namespaces~ read them out, and ~AS=~ says how they are written: ~text~; ~edn~, the data the others are drawn from; ~org~, a table; ~mermaid~, a diagram.

A part of an Org document that is built this way is a dynamic block, so the document says of itself what was written by hand and what was not:

#+begin_example
,#+BEGIN: workshop :view namespaces :as mermaid :from "spectre.cli spectre.tui2"
,#+END:
#+end_example

~gmake blocks~ replaces what is between the two lines, in every Org file at the top of the repo. ~CHECK=1~ writes nothing and fails when a block is behind the files. ~:view~ is ~namespaces~ or ~files~, ~:as~ is one of the four, and the other parameters are that view's options. A file that Emacs holds with unsaved edits is left alone.

To look at one without putting it anywhere, ~gmake draw~ pipes a view through mermaid-cli. The extension of ~OUT~ picks the image, and the view's options pass through:

#+begin_src sh :eval no
gmake draw OUT=~/Desktop/namespaces.png NS="spectre.cli spectre.tui2" PROGRESS=1
gmake draw OUT=~/Desktop/files.svg VIEW=files
#+end_src

~mmdc~ starts a browser and has to be told which. The target hands it ~puppeteer/config.json~ from your configuration directory when there is one, and ~PUPPETEER_CONFIG=~ names another. A block is drawn from inside Emacs by ~ob-mermaid~ when its first line also gives ~:file~ and ~:puppeteer-config-file~.

This much is a scaffold. No document has such a block yet, and [[file:.meta/README.md][.meta/README.md]] has what is left to decide.

** The reference shelf

~gmake resources~ fetches the manuals for what is installed here into ~resources/~, which git ignores: the API of the ~babashka.fs~ compiled into this ~bb~, the manual of the CIDER this Emacs loads, the Info files of this Emacs. [[file:dev/resources.edn][dev/resources.edn]] is the list. ~resources/INDEX.org~ says what was fetched, at which version, from where. A second run fetches only what has moved: a tool upgraded, or an entry edited.

|-----------------------------------+------------------------------------------------------------------------------------------------------|

| an ~fs/~ or ~p/~ call (E2, E3)    | ~babashka/fs/API.md~, ~babashka/process/API.md~: one heading for each function                       |

Search it by naming it. ripgrep skips an ignored directory unless it is given one.

#+begin_src sh :eval no
rg -n 'name="babashka.fs/which"' resources/babashka/fs/API.md   # one function: read from that line
rg -n 'cider-eval-last-sexp' resources/emacs/cider              # a command, across the CIDER manual
bb -e '(-> (slurp "resources/clojure/clojuredocs/export.compact.edn") clojure.edn/read-string :clojure.core/merge-with :examples first println)'
#+end_src

The documents are other people's, so none of it is committed. ~gmake guard-resources~ fails when anything under ~resources/~ is tracked or in history: run it before a push. In a document, write a shelf path as code and not as a link; ~gmake docs~ refuses the link, which would work here and nowhere else.

There is one shelf for the clone, in the main checkout. In a worktree ~gmake resources~ makes ~resources~ a link to it. A file of your own put there is left alone, and the index lists it apart.

The CIDER, clojure-mode and lsp-mode entries are copied from the checkout the running Emacs loads each library from, which it is asked for. With no Emacs running they are kept as they are. A library that package.el installed has no manual beside it, and its entry is skipped.

** Emacs

[[file:babashka-workshop-spectre.el][babashka-workshop-spectre.el]] is the wiring, and its commentary lists the commands. ~gmake demo~ and ~gmake session~ load it. It jacks CIDER in to babashka, puts clj-kondo's findings in the buffer through Flymake, makes ~C-c C-c~ inside a ~comment~ block evaluate one form, shows keystrokes in the header line when keycast is installed, and keeps a log of every nREPL message. ~M-x spectre-test-ns~ runs the tests for the buffer's namespace.

** For an agent

~.claude/settings.json~ has two hooks: the session status is put in context at start, and every Write and Edit of a Clojure file has its delimiters balanced and is formatted with cljfmt. ~dev/claude-plugins/~ is a local plugin that puts ~clojure-lsp~ behind Claude Code's LSP tool. [[file:AGENTS.md][AGENTS.md]] is the contract.

** An operator

~gmake claude~ puts Claude Code in a tmux session of its own for this checkout, ~spectre-claude~ here and ~spectre-<dir>-claude~ in a worktree. It makes the session when there is none, starts Claude when the session's pane is at a shell, and attaches. A second run only attaches. ~gmake claude-status~ prints what that pane is running and its last lines, and changes nothing.

Claude is started with ~--permission-mode auto~, which is for an operator nobody is sitting with; ~CLAUDE_FLAGS=~ takes it out. It is started with ~-c~ when this directory already has a conversation. From inside a Claude session that is not in tmux the target refuses: ~-c~ there would open that session's own conversation a second time.

What it cannot tell:

- A pane whose command is not a shell is taken to have an operator in it. One left in an editor or a long build looks the same.
- Only the session's active pane is looked at.
- ~-c~ continues the most recent conversation in the directory, whichever that was.
- Where Claude keeps a directory's conversations is read off this machine, not off documentation.

An unattended operator needs a brief it can follow alone. There is none here yet.

** Checkouts

~main~ carries the tooling. Exercises are worked on branches in ~worktrees/~, each with its own ~db.edn~, nREPL port, bbin directory and tmux session, derived in ~.envrc~. A new worktree needs ~gmake .env~ and ~direnv allow~ once.
